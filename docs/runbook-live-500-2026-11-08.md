# Runbook: Live 500 on every route after deploy — 2026-11-08

## What happened

A change passed the local checks (`vite build` and the test suite) and was
deployed. On the live site, every route returned HTTP 500.

The cause was in the SSR worker bundle: a module-initialisation crash. An
import cycle in the bundled server code dereferenced an imported binding at
module top level, before that binding was initialised, so the worker threw
during startup and could not serve any route.

The deploy pipeline builds with `build:worker` (the SSR bundle). The local
verification for that change had only run the regular `vite build` plus
tests — the worker bundle was never built or served locally, so the crash
class was invisible until production.

## How it was detected

Every route on the live URL returned 500. The failure was total rather than
limited to one page, which pointed at worker startup (module
initialisation) rather than a single route's code.

## How it was fixed

The cyclic top-level dereference in the server bundle was removed so module
initialisation no longer depends on an uninitialised binding, and the fixed
build was redeployed.

## Standing rule (prevents recurrence)

No slice is called ready until all of the following have run against the
exact tree being shipped:

1. `npm run build:worker` succeeds.
2. The built output is served locally
   (`npx wrangler dev --config .output/server/wrangler.json --port <port>`
   from the repo root).
3. Three curls against the served build return the expected results:
   `/` → 200, one app route → 200, a nonsense path → branded 404.

`vite build` and the test suite alone are not a sign-off: they cannot catch
this crash class.

## If this happens again

- [ ] Confirm the scope: curl `/`, one app route, and a nonsense path on
      the live URL. All-500 means worker startup; one-route-500 means route
      code.
- [ ] Reproduce locally before changing anything: `npm run build:worker`,
      serve `.output/server`, repeat the same three curls.
- [ ] Read the worker's startup error; look first for a module-init throw
      (import cycle, top-level dereference of an imported binding).
- [ ] Fix the cause, add a regression test where the code allows one, then
      re-run the full standing-rule sign-off (build:worker + served smoke)
      before redeploying.
- [ ] If the site must be restored before the fix is understood, redeploy
      the last known-good build, then diagnose on the local served build.
